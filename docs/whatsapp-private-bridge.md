# Private VPS bridge: registration checks

The CRM runs on Vercel; WA-AKG binds only to 127.0.0.1:3300 on the VPS.
Vercel cannot use the operator's laptop SSH tunnel. This bridge leaves the
gateway private: a Python standard-library worker on the VPS makes outbound
HTTPS requests to the CRM. No new VPS port, reverse proxy or Jack/OpenClaw
configuration is needed.

## Credentials and deployment

1. Generate a separate 32+ character random secret and save it on the VPS as
   `/opt/fencely-wa/crm-bridge-secret` with mode 0600. Store the same value in
   the CRM's Vercel Production environment as `WA_BRIDGE_SECRET` and redeploy
   this code. Do not use the gateway key, login JWT or MCP token for this.
2. Keep the existing gateway key in `/opt/fencely-wa/crm-api-key` on the VPS.
   Do not put it in Vercel, frontend code or GitHub.
3. Copy `integrations/wa-akg/private-worker.py` to
   `/opt/fencely-wa/private-worker.py` on the VPS. Check its SHA before use.
4. Create `/opt/fencely-wa/worker.env` with mode 0600 on the VPS. Set
   `CRM_ORIGIN` to your actual CRM HTTPS origin and `WA_AKG_SESSION_ID` to the
   gateway sessionId (not the database row ID). Keep these installation-specific
   values out of public repositories. The service reads this environment file.
5. Install the unit as `/etc/systemd/system/fencely-checks.service`, then run
   `systemctl daemon-reload` and `systemctl enable --now fencely-checks`.
   This creates one separate service; it does not restart Docker or OpenClaw.
6. Inspect `systemctl status fencely-checks --no-pager` and
   `journalctl -u fencely-checks -n 20 --no-pager`.

The service uses at most 128 MB and 10% of one CPU, runs no listener, and polls
once a minute (about 43,200 idle CRM calls in 30 days, plus results). Check the
actual hosting allowance. The worker needs root read access to the two secret
files; it runs with no new privileges, read-only system files and private temp.

## Behavior and validation

An authenticated Check WhatsApp click (or MCP tool) queues a registration read.
The UI acknowledges the queue; reopen the lead after about a minute to see the
result. Configure WA_BRIDGE_SECRET on the local stdio MCP process too if it
should use this mode. Without that secret, the old direct gateway mode remains.

Only the target number and opaque job/lease IDs go to the worker. Separate
worker routes accept this credential only; they cannot read the full CRM or
change stages/contact logs. Claims use atomic SQLite UPDATE RETURNING, safe
across serverless processes. A 120-second lease lets read-only checks recover
from worker loss. Repeated clicks coalesce; repeated acknowledgements do not
create duplicate activities. Changed/deleted leads reject stale results.

The worker rejects redirects, sends gateway requests only to loopback, and
never prints keys, phone numbers, response bodies or job payloads. Result text
and timestamps are generated by the CRM. Negative checks remain unconfirmed;
network/authentication errors do not mean no WhatsApp.

Validated locally: 24 Node tests including worker authentication, duplicate
clicks, concurrent leases, expired credentials, edited/deleted numbers,
idempotent completion and HTTP queue/result flow; frontend production build;
Python syntax and mocked gateway verdict cases. No real lead number was checked
by the assistant. Live Turso/Vercel-to-VPS flow still requires a user-owned test
record after deployment.

## Scope

This stage never sends a message. It does not implement incoming reply sync,
STOP suppression, campaign scheduling, follow-ups or AI generation. Button
clicks observed in WA-AKG alone do not yet change the CRM. Do not launch a live
campaign until those parts are implemented and tested.

To stop/remove only the worker: `systemctl disable --now fencely-checks`, remove
its unit and script, and remove WA_BRIDGE_SECRET from Vercel. Existing gateway
sessions, CRM records and Jack's services are separate.
